## Plan: Stitch UI and Admin to Backend

Wire the two React/Vite frontends to the backend so the main app can exercise auth, generation, payments, and account state, while the admin app can exercise admin-only management endpoints. The UI should read `/api/v1/config/public` and switch its auth experience by the configured backend auth mode, but present user-facing labels as SMS or Email. The goal is to test the implemented backend logic end-to-end without redesigning the apps.

**Steps**
1. Update the shared API client and public-config bootstrap in both apps so they talk to the backend base URL from `VITE_API_URL` and fetch `/api/v1/config/public` on startup. *Depends on nothing; this is the shared anchor for the rest of the work.*
2. Rework the main UI auth flow so the login screen branches by the public `authMode` value and shows the correct user-facing path: SMS OTP when the backend is in phone mode, email/Microsoft-style sign-in when the backend is in Microsoft mode, with form submission handlers for the actual backend endpoints. *Depends on step 1.*
3. Replace the placeholder creation screens in the main UI with real calls for upload intent, generation creation, credit checks, and job status/navigation, so PixArt and comic flows can be exercised against the backend. *Depends on step 1 and step 2.*
4. Connect the main UI account pages to authenticated endpoints for me/logout, credits, payments, generations, and download links, with loading/error states that reflect backend responses instead of static placeholders. *Depends on steps 1-3.*
5. Build the admin app around the backend admin endpoints: login gate, dashboard metrics, users table, generation jobs table, payments/webhooks views, and audit log views. *Depends on step 1 and the backend admin routes already exposed.*
6. Add shared auth/session handling for both apps so credentialed requests work consistently, the current user can be discovered on load, and logout clears the local session state cleanly. *Parallel with steps 2-5 once the API client is in place.*
7. Update the sample env files and any local README copy so the auth-mode switch is clear: backend `AUTH_MODE` controls the UI labels, while storage can stay mocked or disabled for local testing. *Depends on the final shape of the frontend wiring.*
8. Validate the stitched flows end to end: login, current-user fetch, upload intent, generation creation, admin access, and logout. Use the existing backend plus the two dev servers to confirm requests, cookies, and route guards behave correctly. *Depends on all prior steps.*

**Relevant files**
- `ui/src/App.tsx` - main user flows, auth branching, generation entry points, account pages.
- `ui/src/main.tsx` - app bootstrap, query client/provider setup if needed.
- `ui/src/index.css` and `ui/src/App.css` - styling for the stitched flows and auth screens.
- `ui/.env.example` - document `VITE_API_URL` and auth-mode expectations.
- `admin/src/App.tsx` - admin routes, login gate, dashboard/table wiring.
- `admin/src/main.tsx` - app bootstrap and shared client/provider setup if needed.
- `admin/src/index.css` and `admin/src/App.css` - admin layout and data-table styling.
- `admin/.env.example` - document `VITE_API_URL` for admin API access.
- `api/internal/httpapi/routes.go` - confirm the frontend path names match the backend endpoints and auth mode behavior.
- `api/.env.example` - clarify backend `AUTH_MODE`, storage mode, and local dev defaults.

**Verification**
1. Build both frontends: `cd ui && npm run build` and `cd admin && npm run build`.
2. Run both dev servers and confirm the login screen changes when backend `AUTH_MODE` is switched between phone and microsoft.
3. Exercise the backend flow through the UI: authenticate, fetch `/api/v1/auth/me`, create an upload intent, start a generation, and confirm job state changes.
4. Open the admin app and confirm the dashboard, users, generations, and audit views load from the protected endpoints with a valid admin session.
5. Check browser network traffic for cookie-based requests and verify CORS/credentialed access remains intact.

**Decisions**
- User-facing auth labels should be SMS and Email, while the backend mode still controls the actual route selection.
- Preserve the existing visual structure and do not introduce a new design system; the task is stitching and functional coverage, not a full redesign.
- Keep storage mocked or disabled for local testing unless a real local filesystem flow is explicitly needed for a specific screen.

**Further Considerations**
1. If you want the main UI to support both SMS and Email in one build, the backend `AUTH_MODE` should be treated as the source of truth and only the labels should change.
2. If the admin login must use a separate auth path from the main app, we should align that with the backend session model before wiring the screens.
